## 1. 시스템 구성 요소

| 구성요소 | 역할 | 기술 스택(제안) |
|---|---|---|

**② KPI 카드 (FN-210)**
| 카드 | 계산식 | 비교 기준 |
|---|---|---|
| 총 매출 | `SUM(sales_amount)` | 직전 동일 길이 기간 |
| 결제건수 | `SUM(order_count)` | 동상 |
| 객단가 | `총매출 ÷ 결제건수` | 동상 |
| 일평균 매출 | `총매출 ÷ 영업일수` | 동상 (휴무일 제외) |

- 증감률 = `(현재 − 이전) ÷ 이전 × 100`, 소수 1자리
- 이전 기간 데이터 없으면 "비교 데이터 없음" 표시
- 증감 표기: ▲ 상승 / ▼ 하락 / — 변화없음 + 색상 병기

**④-2 지난주 같은 요일 대비 (FN-235)**

"지난주 수요일보다 올랐나?" 를 한 눈에 보기 위한 표다. 요일별 평균(FN-230)은
평균이라 특정 주의 변화를 못 보여준다.

| 항목 | 사양 |
|---|---|
| 형태 | 표 4열 — 요일 / 지난주 / 이번주 / 증감 |
| 행 | 월~일 7행 + 합계 1행 |
| 기준 주 | **조회 기간 안에서 매출이 있는 마지막 날이 속한 월~일.** 종료일을 그대로 쓰면 수집이 밀렸을 때 표가 통째로 빈다 |
| 지난주 | 기준 주에서 정확히 7일 전 구간 |
| 각 칸 | 금액(만원 축약, 정확값은 title) + 날짜(MM/DD) |
| 결측 처리 | 휴무는 "휴무", 미수집·미래는 "—". **0원으로 채우지 않는다** |
| 증감 | 한쪽이라도 값이 없으면 `null` → "—". 0원으로 치면 ▼100%가 된다 |
| 합계 | **양쪽 다 매출이 있는 요일만** 더한다. 3일 합계와 7일 합계를 비교하면 매출이 반토막 난 것으로 오해한다 |

**④-3 연도별 매출 (FN-236 / FR-DASH-16)**

| 항목 | 사양 |
|---|---|
| 위치 | 대시보드 **맨 아래** (메뉴 순위 다음) |
| 형태 | 막대 — 연도당 막대 하나, 가장 최근 해 강조 |
| 값 라벨 | 막대 바로 위에 **말로 읽는 금액** — `11억 1천7백만원`, `6천3백만원` (`format.shortWon` — 8.4장). 정확값은 툴팁 |
| 범위 | **기간 필터와 무관. 마감된 해만** (2021~2025). POS 조회 하한 2021-01-01 (`docs/03` 5-1장) |
| 마감 판정 | **다음 해 데이터가 하나라도 있으면 마감.** 날짜로 판정하지 않는다 — 12/31 수집 전에 막대가 뜨면 안 된다. 2026년은 2027-01-02 04시 자동 수집 때 손대지 않아도 붙는다 |
| 부분 연도 | 1월 1일~12월 31일을 다 갖지 못한 해는 X축에 실제 기간(MM/DD~MM/DD)을 함께 적는다. 합계만 보면 진행 중인 해가 늘 진 것처럼 보인다 |
| 툴팁 | 매출, 영업일수, 일평균, 결제건수 |
| 메뉴 데이터 | 2025-08-20 이전은 **주문·취소만** 소급했다(`--skip-menu`). 그 기간을 조회하면 매출·시간대는 나오고 메뉴 순위는 비어 있다 |

**⑥-0 신메뉴 매출 (FN-252)** — 메뉴 순위 **위**에 둔다

새로 들인 메뉴는 아직 양이 적어 TOP 10에 올라오지 않는다. 정작 사장님이 가장
궁금해하는 숫자인데 화면에서 사라져 있으므로 따로 뗀다.

| 컬럼 | 내용 |
|---|---|
| 첫 판매일 | `YY.MM.DD` — 순위 자리를 대신한다. 이 표의 핵심은 '언제부터'다 |
| 메뉴명 | FN-251 별칭 적용 + 배지(`신규 N일째` / `직접 지정`) |
| 판매수량·비중 | 선택 기간 기준 |
| 금액 | 세 가지로 갈린다 — 금액 / `옵션`(수량만 있고 0원) / `판매 없음`(수량 0) |

- 합계 줄: `신메뉴 N개 중 M개 판매 · 수량 · 매출 · 전체 메뉴 매출의 X%`
- **합계는 매출이 발생한 신메뉴만 더한다.** 0원 옵션의 수량을 섞으면 숫자가 거짓말을 한다
  (실측: 섞으면 4,272개, 실제 판매 메뉴는 152개)
- 신메뉴가 없으면 빈칸이 아니라 안내 문구 + [기준 설정] 버튼을 남긴다 (FN-262)

**⑥-1 신메뉴 기준 (FN-253 / FR-DASH-15)**

POS는 **메뉴 등록일을 주지 않는다.** `menus.first_seen` 은 수집 시각이라 쓸 수 없다
(백필을 한 번에 돌리면 전 메뉴가 같은 값이 된다). 그래서 `MIN(menu_sales.biz_date)`
= **첫 판매일**을 등록일의 근사치로 쓴다.

| 규칙 | 내용 |
|---|---|
| 기본 | 조회 기간 **종료일 기준 3개월**. `1 / 3 / 6 / 12개월` 또는 기준일 직접 지정 |
| 분류 | 기본 **`월남쌈샤브샤브` 하나**. 화면에서 여러 개 켜거나 `전체` 선택 가능 |
| 창의 양 끝 | `기준일 ≤ 첫 판매일 ≤ 조회 종료일`. 위쪽 끝이 없으면 8월을 보는데 10월 메뉴가 낀다 |
| 워밍업 제외 | 관측 시작 후 **30일** 안에 첫 판매된 메뉴는 자동 판정에서 뺀다 |
| 수동 지정 | `지정 / 제외 / 자동` 3단. **지정이 자동 판정을 이긴다** (워밍업 제외까지) |
| 예외 | 조회 종료일까지 한 번도 안 팔린 메뉴는 지정해도 안 나온다 — 그때 없던 메뉴다 |
| 저장 위치 | DB (`app_settings` / `menu_overrides`). 휴대폰·PC에서 같은 설정이 보여야 한다 |
| 단일 출처 | `server/service/new_menu.py` |

워밍업 제외가 필요한 이유: 드물게 팔리는 오래된 메뉴는 관측 시작 직후에야 처음
팔린다. 가드가 없으면 기준 12개월에서 **100개 중 71개**가 "신규"로 잡혔다.

분류 필터가 필요한 이유: POS `기타` 분류에는 메뉴가 아니라 옵션(`성인`·`반반`·`목심`)이
들어 있다. 2026-08-18 에 그 분류가 생기며 13개가 한꺼번에 잡혔다. 사장님이 보려는 것은
새로 들인 **요리**다. 다만 **분류를 코드에 고정하지 않는다** — `토마토샤브` 는 120g 이
`월남쌈샤브샤브`, 70g 이 `점심특선` 이라 하나만 걸면 같은 신메뉴의 반쪽이 사라진다.
칩 목록도 박아 두지 않고 실제 데이터에 있는 분류로 만든다.

근사치의 한계는 두 방향이다 — ① 드물게 팔리는 오래된 메뉴가 잡힌다
② 등록만 하고 아직 안 팔린 메뉴는 안 잡힌다. ②는 자동으로 알 길이 없으므로
수동 지정이 반드시 필요하다.

### 5.2-2 수동 수집 (FN-205)

읽기 전용 조회와 달리 **POS에 실제 요청을 유발한다.** 그래서 라우터를 분리했다
(`server/routers/system.py`). 누가 실제로 수집하는지는 `server/collect_trigger.py`가 판단한다.

#### `GET /api/system/collect/status`
```jsonc
{
  "backend": "local",          // local | github | none
  "available": true,           // false 면 화면이 버튼을 숨긴다
  "running": false,
  "startedAt": "2026-09-08T22:41:36+09:00",
  "finishedAt": "2026-09-08T22:42:19+09:00",
  "ok": true,
  "message": "수집을 마쳤습니다.",
  "retryAfterSec": 0           // > 0 이면 최소 간격 안 — 버튼 비활성
}
```

#### `POST /api/system/collect`
성공 시 위와 같은 형태에 `running: true`. **거절도 정상 동작이다** — POS에 요청이
겹쳐 나가지 않게 막는 것이 목적이다.

| 상태 | code | 뜻 |
|---|---|---|
| 409 | `ALREADY_RUNNING` | 이미 수집 중 (탭을 여러 개 열었을 때) |
| 429 | `TOO_SOON` | 최소 간격 안. `Retry-After` 헤더로 남은 초를 알려준다 |
| 503 | `UNAVAILABLE` | 이 환경에는 트리거할 수단이 없다 |
| 502 | `TRIGGER_FAILED` | GitHub Actions를 깨우지 못했다 |

**백엔드가 둘인 이유.** Vercel 함수는 10초에서 끊기지만 수집은 30초~1분 걸린다.
게다가 사장님이 접속하는 쪽에 POS 계정을 두지 않는다 (CLAUDE.md 보안 규칙).
그래서 배포판은 직접 수집하지 않고 GitHub Actions에게 부탁만 한다.

| 백엔드 | 조건 | 동작 |
|---|---|---|
| `local` | `POS_USER_ID` / `POS_USER_PW` | 백그라운드 스레드에서 `collect_yesterday()` |
| `github` | `DISPATCH_REPO` / `DISPATCH_TOKEN` | Actions `workflow_dispatch` 호출 |
| `none` | 둘 다 없음 | 버튼 숨김 |

```sql
  store_name    VARCHAR(100) NOT NULL,         -- '소담촌 마곡점'
  open_hour     SMALLINT DEFAULT 11,
  close_hour    SMALLINT DEFAULT 22,
  created_at    TIMESTAMPTZ DEFAULT NOW()
);

-- 대시보드 사용자 (POS 계정과 분리)
CREATE TABLE users (
  user_id       SERIAL PRIMARY KEY,
  store_id      INT REFERENCES stores(store_id),
  username      VARCHAR(50) UNIQUE NOT NULL,
  password_hash VARCHAR(255) NOT NULL,         -- bcrypt
  role          VARCHAR(20) DEFAULT 'owner',   -- owner | manager | admin
  last_login_at TIMESTAMPTZ,
  created_at    TIMESTAMPTZ DEFAULT NOW()
);

-- 일별 매출
CREATE TABLE daily_sales (
  store_id      INT REFERENCES stores(store_id),
  biz_date      DATE NOT NULL,
  sales_amount  BIGINT,
  order_count   INT,
  discount_amt  BIGINT DEFAULT 0,
  cancel_amt    BIGINT DEFAULT 0,
  is_closed     BOOLEAN DEFAULT FALSE,
  updated_at    TIMESTAMPTZ DEFAULT NOW(),
  PRIMARY KEY (store_id, biz_date)
);

-- 메뉴 마스터
CREATE TABLE menus (
  menu_id       SERIAL PRIMARY KEY,
  store_id      INT REFERENCES stores(store_id),
  menu_code     VARCHAR(50) NOT NULL,
  menu_name     VARCHAR(200) NOT NULL,
  category      VARCHAR(50),
  unit_price    INT,
  is_active     BOOLEAN DEFAULT TRUE,
  UNIQUE (store_id, menu_code)
);

-- 메뉴별 일 판매
CREATE TABLE menu_sales (
  store_id      INT,
  biz_date      DATE,
  menu_id       INT REFERENCES menus(menu_id),
  quantity      INT,
  sales_amount  BIGINT,
  PRIMARY KEY (store_id, biz_date, menu_id)
);

-- 시간대별 매출
CREATE TABLE hourly_sales (
  store_id      INT,
  biz_date      DATE,
  hour          SMALLINT CHECK (hour BETWEEN 0 AND 23),
  sales_amount  BIGINT,
  order_count   INT,
  PRIMARY KEY (store_id, biz_date, hour)
);

-- 수집 로그
CREATE TABLE collection_logs (
  log_id        SERIAL PRIMARY KEY,
  store_id      INT,
  started_at    TIMESTAMPTZ,
  finished_at   TIMESTAMPTZ,
  target_from   DATE,
  target_to     DATE,
  status        VARCHAR(20),      -- success | partial | failed
  record_count  INT,
  error_message TEXT
);

-- 원본 보존
CREATE TABLE raw_payloads (
  raw_id        BIGSERIAL PRIMARY KEY,
  store_id      INT,
  biz_date      DATE,
  source_type   VARCHAR(50),      -- daily | menu | hourly
  payload       JSONB,
  collected_at  TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_daily_date  ON daily_sales(store_id, biz_date DESC);
CREATE INDEX idx_menu_date   ON menu_sales(store_id, biz_date DESC);
CREATE INDEX idx_hourly_date ON hourly_sales(store_id, biz_date DESC);
```

## 7. 주요 시퀀스

### 7.1 로그인 → 대시보드 진입
```
사용자        Dashboard UI       Auth API         DB
  │                │                │              │
  ├─ URL 접속 ────►│                │              │
  │                ├─ GET /auth/session ──────────►│
  │                │◄── 401 미인증 ─────────────────┤
  │◄─ 로그인 화면 ──┤                │              │
  ├─ ID/PW 입력 ──►│                │              │
  │                ├─ POST /auth/login ───────────►│
  │                │                ├─ 사용자 조회 ►│
  │                │                │◄─ hash ──────┤
  │                │                ├─ bcrypt 검증 │
  │                │◄── 200 + 세션쿠키 ─────────────┤
  │◄─ 대시보드 ────┤                │              │
```

### 7.2 대시보드 데이터 로드 (병렬)
```
Dashboard UI ─┬─► GET /api/summary        ─┐
              ├─► GET /api/sales/daily    ─┤
              ├─► GET /api/sales/weekday  ─┼─► Data API ─► DB(집계 조회)
              ├─► GET /api/sales/hourly   ─┤
              ├─► GET /api/menu/ranking   ─┤
              └─► GET /api/system/status  ─┘
                  (응답 도착 순으로 위젯 개별 렌더링)
```

### 7.3 일일 자동 수집
```
Scheduler ─(04:00)─► Collector ─► POS 로그인 ─► 데이터 조회
                          │                        │
                          │◄───────────────────────┘
                          ├─► 정제/검증
                          ├─► DB UPSERT
                          └─► collection_logs 기록
                                    │
                              실패 시 └─► 알림 발송
```
