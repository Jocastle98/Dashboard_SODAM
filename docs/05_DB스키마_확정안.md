### 4번의 의미 — 파서의 첫 번째 규칙

```
주문 리포트의 <table> 구조:
  [0] 3행 x 1열     제목/기간/출력일자
  [1] 2행 x 20열    헤더 (중첩)
  [2] 1행 x 19열    헤더 (중첩)
  [3] 52행 x 970열  ← 중첩표가 이어붙은 것. 버릴 것
  [4] 51행 x 19열   ← 진짜 데이터 (합계 1 + 주문 50)
```

**규칙: 목표 열 수와 일치하는 표 중 행이 가장 많은 것 하나만 쓴다.**
모든 표의 행을 합치면 정확히 2배가 되어, 매출이 2배로 부풀어도 오류가 나지 않는다.

## 3. 스키마

> SQLite 방언으로 작성한다. PostgreSQL 이식을 위해
> `SERIAL` → `INTEGER PRIMARY KEY AUTOINCREMENT`, `TIMESTAMPTZ` → ISO8601 `TEXT`,
> `BOOLEAN` → `INTEGER(0/1)` 로 두고, 배포 시 타입만 바꾼다.

### 3.1 `stores` — 매장

```sql
CREATE TABLE stores (
  store_id      INTEGER PRIMARY KEY AUTOINCREMENT,
  store_code    TEXT    NOT NULL UNIQUE,   -- 'SODAM_MAGOK'
  store_name    TEXT    NOT NULL,          -- '소담촌 마곡점'
  pos_branch    TEXT    NOT NULL,          -- 🆕 'sodam001'  POS 조회 키
  pos_brandcode TEXT,                      -- 🆕 '00000'     기록용
  open_hour     INTEGER DEFAULT 11,
  close_hour    INTEGER DEFAULT 22,
  created_at    TEXT    DEFAULT (datetime('now'))
);
```

`pos_branch`를 넣는 이유: 수집기가 매장별로 어떤 값으로 조회할지 DB가 알아야
다점포 확장(`ASM-04`) 시 코드 수정 없이 늘릴 수 있다.

### 3.2 `users` — 대시보드 사용자 (FS 그대로)

```sql
CREATE TABLE users (
  user_id       INTEGER PRIMARY KEY AUTOINCREMENT,
  store_id      INTEGER NOT NULL REFERENCES stores(store_id),
  username      TEXT    NOT NULL UNIQUE,
  password_hash TEXT    NOT NULL,          -- bcrypt (FR-AUTH-04)
  role          TEXT    DEFAULT 'owner',
  last_login_at TEXT,
  created_at    TEXT    DEFAULT (datetime('now'))
);
```

### 3.3 `orders` — 🆕 주문(영수증) 단위 원본

POS 19컬럼 중 대시보드에 필요한 것만 담는다.

```sql
CREATE TABLE orders (
  store_id      INTEGER NOT NULL REFERENCES stores(store_id),
  order_no      TEXT    NOT NULL,          -- '202608150001'
  biz_date      TEXT    NOT NULL,          -- '2026-08-15'  order_no 앞 8자
  sold_at       TEXT    NOT NULL,          -- '2026-08-15 11:02'  판매시간
  paid_at       TEXT,                      -- '2026-08-15 12:21'  결제시간
  total_amt     INTEGER NOT NULL DEFAULT 0,  -- 총매출액
  discount_amt  INTEGER NOT NULL DEFAULT 0,  -- 할인액
  net_amt       INTEGER NOT NULL DEFAULT 0,  -- 순매출액
  vat_amt       INTEGER NOT NULL DEFAULT 0,  -- 부가세
  cash_amt      INTEGER NOT NULL DEFAULT 0,
  card_amt      INTEGER NOT NULL DEFAULT 0,
  gift_amt      INTEGER NOT NULL DEFAULT 0,  -- 상품권
  point_amt     INTEGER NOT NULL DEFAULT 0,
  credit_amt    INTEGER NOT NULL DEFAULT 0,  -- 외상결제
  prepaid_amt   INTEGER NOT NULL DEFAULT 0,  -- 선수금
  card_issuer   TEXT,                        -- 카드사
  card_acquirer TEXT,                        -- 매입사
  table_name    TEXT,                        -- 테이블명
  collected_at  TEXT    DEFAULT (datetime('now')),
  PRIMARY KEY (store_id, order_no)
);
CREATE INDEX idx_orders_date ON orders(store_id, biz_date DESC);
CREATE INDEX idx_orders_sold ON orders(store_id, sold_at);
```

**저장하지 않는 컬럼:**

| POS 컬럼 | 사유 |
|---|---|
| `No.` | 조회 시점 순번일 뿐 고유값이 아님 |
| `매장명` | `store_id`로 대체 |
| **`승인번호`** | **카드 거래 식별자. 대시보드에 불필요하고 보관 위험** (`6.3 개인정보 미수집`) |

`PRIMARY KEY (store_id, order_no)` 가 `FR-COL-05`/`FN-604` 멱등성을 보장한다.
같은 날짜를 다시 수집해도 UPSERT로 갱신될 뿐 중복되지 않는다.

### 3.4 `daily_sales` — 일별 집계 (파생)

FS 명세를 유지하되 **`orders`에서 재생성 가능한 파생 테이블**로 성격을 바꾼다.

```sql
CREATE TABLE daily_sales (
  store_id      INTEGER NOT NULL REFERENCES stores(store_id),
  biz_date      TEXT    NOT NULL,
  sales_amount  INTEGER,                  -- SUM(total_amt)
  order_count   INTEGER,                  -- COUNT(*)
  discount_amt  INTEGER DEFAULT 0,
  cancel_amt    INTEGER DEFAULT 0,        -- order_cancels에서
  vat_amt       INTEGER DEFAULT 0,
  cash_amt      INTEGER DEFAULT 0,
  card_amt      INTEGER DEFAULT 0,
  etc_amt       INTEGER DEFAULT 0,        -- 상품권+포인트+외상+선수금
  is_closed     INTEGER DEFAULT 0,        -- DQ-02
  updated_at    TEXT    DEFAULT (datetime('now')),
  PRIMARY KEY (store_id, biz_date)
);
CREATE INDEX idx_daily_date ON daily_sales(store_id, biz_date DESC);
```

**`is_closed` 판정 규칙 (`DQ-02`, `FR-DASH-12`):**

| 상황 | `daily_sales` 행 | `is_closed` | 대시보드 |
|---|---|---|---|
| 주문 있음 | 있음 | `0` | 정상 표시 |
| 수집 성공했는데 주문 0건 | 있음 | `1` | "휴무" 마커 |
| 아직 수집 안 함 / 수집 실패 | **행 없음** | — | 선 끊김 (미수집) |

> ⚠ POS는 휴무 여부를 알려주지 않는다. "수집에 성공했고 주문이 0건"이라는
> 사실로 추론하는 것이며, 이는 가정이다. `collection_logs`에 수집 성공 기록이
> 있는지로 판단한다. 사장님이 실제 휴무일을 알려주시면 `SCR-05`(`FN-504`)에서
> 보정할 수 있게 둔다.

### 3.5 `hourly_sales` — 시간대별 (파생)

**`timeAnal` 리포트를 수집하지 않고 `orders.sold_at`에서 유도한다.** (0장 검증 1번)

```sql
CREATE TABLE hourly_sales (
  store_id      INTEGER NOT NULL REFERENCES stores(store_id),
  biz_date      TEXT    NOT NULL,
  hour          INTEGER NOT NULL CHECK (hour BETWEEN 0 AND 23),
  sales_amount  INTEGER,
  order_count   INTEGER,
  PRIMARY KEY (store_id, biz_date, hour)
);
CREATE INDEX idx_hourly_date ON hourly_sales(store_id, biz_date DESC);
```

날짜별로 저장하므로 `FR-DASH-05`(시간대 차트)와 공모전 보완 1순위인
**요일×시간 히트맵**을 둘 다 만들 수 있다.

### 3.6 `menus` / `menu_sales` — 메뉴 (FS 그대로)

```sql
CREATE TABLE menus (
  menu_id     INTEGER PRIMARY KEY AUTOINCREMENT,
  store_id    INTEGER NOT NULL REFERENCES stores(store_id),
  menu_code   TEXT    NOT NULL,           -- '000012'  앞 0 유지 위해 TEXT
  menu_name   TEXT    NOT NULL,           -- '월남쌈샤브(120g)'
  category    TEXT,                       -- '월남쌈샤브샤브'  POS 분류명
  first_seen  TEXT    DEFAULT (datetime('now')),
  last_seen   TEXT,
  is_active   INTEGER DEFAULT 1,
  UNIQUE (store_id, menu_code)
);

CREATE TABLE menu_sales (
  store_id     INTEGER NOT NULL,
  biz_date     TEXT    NOT NULL,
  menu_id      INTEGER NOT NULL REFERENCES menus(menu_id),
  quantity     INTEGER,
  sales_amount INTEGER,
  PRIMARY KEY (store_id, biz_date, menu_id)
);
CREATE INDEX idx_menu_date ON menu_sales(store_id, biz_date DESC);
```

- `menu_code`는 **TEXT**로 둔다. `000012`를 정수로 바꾸면 앞의 0이 날아간다.
- FS의 `unit_price`는 뺀다. POS가 단가를 주지 않는다 (매출÷수량은 할인 때문에 부정확).
- `일평균매출액` 컬럼은 저장하지 않는다. 조회 시 계산되는 파생값이다.
- 메뉴명이 바뀌어도 `menu_code`가 같으면 같은 메뉴로 본다. `last_seen`으로 단종 추적.

### 3.7 `order_cancels` — 🆕 취소 내역

`agentAnal_com_excel03` (품목 단위로 나온다).

```sql
CREATE TABLE order_cancels (
  store_id     INTEGER NOT NULL,
  biz_date     TEXT    NOT NULL,
  order_no     TEXT    NOT NULL,          -- '20260815-0043'
  seq          INTEGER NOT NULL,          -- 같은 주문에 여러 품목
  cancel_type  TEXT,                      -- 구분: '전체취소'
  sold_at      TEXT,                      -- '18:05'  시각만 옴
  canceled_at  TEXT,
  item_name    TEXT,                      -- 품목
  quantity     INTEGER,
  amount       INTEGER,
  reason       TEXT,                      -- 취소사유
  PRIMARY KEY (store_id, biz_date, order_no, seq)
);
```

`DQ-01`(음수 매출 = 취소 건 별도 관리)의 근거 데이터다.
`daily_sales.cancel_amt`는 여기서 집계한다.

> ⚠ 취소 리포트의 주문번호 형식이 주문 리포트와 다르다
> (`20260815-0043` vs `202608150043`). 파서에서 정규화한다.

### 3.8 `collection_logs` — 수집 이력 (FS 그대로 + 리포트 구분)

```sql
CREATE TABLE collection_logs (
  log_id        INTEGER PRIMARY KEY AUTOINCREMENT,
  store_id      INTEGER,
  report_type   TEXT,                     -- 🆕 orders | menu | cancels
  started_at    TEXT,
  finished_at   TEXT,
  target_from   TEXT,
  target_to     TEXT,
  status        TEXT,                     -- success | partial | failed
  record_count  INTEGER,
  error_message TEXT
);
CREATE INDEX idx_logs_recent ON collection_logs(store_id, started_at DESC);
```

`FR-COL-06`, `FN-501`, 그리고 `is_closed` 판정의 근거가 된다.

### 3.9 `raw_files` — 원본 보존 (`raw_payloads` 대체)

```sql
CREATE TABLE raw_files (
  raw_id       INTEGER PRIMARY KEY AUTOINCREMENT,
  store_id     INTEGER,
  report_type  TEXT,                      -- orders | menu | cancels
  target_from  TEXT,
  target_to    TEXT,
  file_path    TEXT,                      -- 'data/raw/2026/08/orders_20260801_20260831.html'
  byte_size    INTEGER,
  sha256       TEXT,
  collected_at TEXT DEFAULT (datetime('now'))
);
```

**FS의 `raw_payloads.payload JSONB`를 쓰지 않는 이유:**
POS 응답은 JSON이 아니라 HTML이고, 월 단위 응답이 700KB에 이른다.
12개월이면 DB에 8MB 이상의 HTML이 들어간다. 파일로 두고 경로·해시만 DB에 남기면
`FN-607`(재처리 대비 원본 보존)을 충족하면서 DB가 가벼워진다.
`data/`는 gitignore 대상이라 실매출이 커밋될 위험도 없다.

## 4. 데이터 흐름

```
POS 리포트 3종
   │
   ├─ 주문 상세 ──► orders ──┬──► daily_sales   (집계)
   │                         └──► hourly_sales  (sold_at에서 시간 추출)
   ├─ 메뉴별 ────► menus + menu_sales
   └─ 취소 ──────► order_cancels ──► daily_sales.cancel_amt
```

`daily_sales`와 `hourly_sales`는 **언제든 `orders`에서 다시 만들 수 있다.**
집계 로직이 틀렸다고 밝혀져도 POS를 다시 조회할 필요가 없다.

## 5. 모듈 구성 (`CLAUDE.md` 모듈화 원칙)

```
collector/
  parse/
    __init__.py
    tables.py      중첩표 제거 · 숫자/날짜 정규화  ← 3종 파서가 공유
    orders.py      주문 리포트 → Order 목록
    menu.py        메뉴 리포트 → MenuSale 목록
    cancels.py     취소 리포트 → Cancel 목록
  aggregate.py     orders → daily_sales / hourly_sales
  repository.py    UPSERT 적재 (SQL은 여기서만)
  main.py          기간 인자 진입점 (조율만)
db/
  schema.sql
tests/
  test_parse_orders.py    data/probe 실제 응답을 픽스처로
  test_parse_menu.py
  test_aggregate.py
```

- `tables.py`가 **중첩표 제거와 콤마/날짜 정규화의 단일 출처**다.
  세 파서가 같은 규칙을 쓰지 않으면 한쪽만 고쳐져 조용히 어긋난다.
- SQL은 `repository.py` 밖으로 나가지 않는다.
- `main.py`에는 로직을 두지 않는다.

## 7. 확인이 필요한 결정 사항

| # | 항목 | 제안 | 대안 |
|---|---|---|---|
| 1 | 메뉴 초기 적재 | **일 단위 365회** (약 6분) | 월 단위 12회 — 임의 기간 메뉴 TOP10 부정확 |
| 2 | 초기 적재 범위 | **12개월** | 24개월도 가능 (소급 확인됨) |
| 3 | `승인번호` 저장 | **저장 안 함** | 저장 시 보관 책임 발생 |
| 4 | 원본 보존 방식 | **파일 + 경로/해시** | DB에 HTML 직접 저장 |
| 5 | `timeAnal` 수집 | **안 함** (주문에서 유도) | 수집해서 교차검증 (+365회) |
| 6 | 휴무일 판정 | 수집 성공 + 주문 0건 → 휴무 | 사장님이 직접 지정 |

### 표 선택 규칙 보강

실측 응답에서는 중첩 래퍼 표의 열 수가 970이라 자연히 걸러졌지만,
그 우연에 기대지 않도록 두 겹으로 막았다.

주문은 주문번호, 메뉴는 메뉴코드, 취소는 순번이 각각 달라
